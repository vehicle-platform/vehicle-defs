# Repository Visibility Inventory (T76, D-135)

> **Status:** Proposed inventory only. Nothing has been moved, renamed, deleted, rewritten, or had its GitHub visibility changed. Every public-build replacement and split option below is **proposed**; all final decisions remain with the user (D-135, card T76).

## 1. Scope and Constraints (D-135, T76)

Under **D-135** (refining **D-033**), the generic platform stays public while vehicle-specific and commercially sensitive material moves to private repositories with the user's approval:

- **Public (stays open):** firmware architecture and generic modules, server, mobile companion app, CAN analyzer, `vehicle-mcp`, the generic signal/OBD/fault catalogs, platform documentation, and thesis material. D-033 rules for public repos remain in force (no keys, passwords, real ride data, VINs, or GPS positions).
- **Private (candidates inventoried below):** reverse-engineered vehicle CAN IDs and DIDs (today `vehicle-defs/dbc/cl250.dbc`, `vehicle-defs/uds/vehicle_cl250.yaml`, and derived/constants/fault-binding files that encode CL250 specifics), the archived `HondaCl250_Telemetry` legacy repository, trained ML/LLM weights or datasets (currently not committed, tracked by policy), and future customer- or product-specific modules (D-078).
- **GitHub Free plan constraints (D-135 item 4, card T76):**
  - Private repositories share **2,000 GitHub Actions minutes/month** (compared to free unlimited minutes on public repositories), so CI workflows in private repos must stay minimal.
  - **Repository rulesets are not available** on private repositories on the GitHub Free plan (and GitHub secret-scanning / push-protection features differ from public repos).
- **Public-history constraint (D-135 item 3, card T76):**
  - Content that has already been published in public commits remains present in any existing clones, forks, and caches. Moving files out of public repos stops future publication; rewriting git history is never done automatically and happens only on the user's explicit decision.
- **Methodology:** audited all 12 platform repositories and `vehicle-workspace` on `main` (2026-11-27) by inspecting `vehicle-defs/uds/vehicle_cl250.yaml` (primary physical addressing `0x18DA10F1` / `0x18DAF110`, fallback `0x7E0` / `0x7E8`, and 40 `0xF4xx` UDS-mapped OBD PIDs `0xF404`..`0xF463`), `dbc/cl250.dbc`, `vehicle/cl250_*.yaml`, `derived/cl250_derived.yaml`, `gen/`, every consumer's `external/vehicle-defs` submodule pin, and grepping consumer code and tests for `cl250`, `honda`, `0x18DA10F1`, `0x18DAF110`, `vehicle_cl250`, `vehicle_constants`, `vehicle_derived`, and the `0xF4xx` DIDs. Note that the 40 DIDs in `uds/vehicle_cl250.yaml` are standard SAE J1979 / ISO 15031-5 PIDs mapped into `0xF400 | PID`, while **which subset the CL250 ECU actually answers, the addressing scheme (`0x18DA10F1`→`0x18DAF110`), padding (`0xAA`), verified/unverified status, poll rates, and physical ratios/dimensions** are CL250-specific facts.

## 2. Per-Repository Inventory

Replacement categories used in the rightmost column (all **proposed**):
- **nothing (proposed):** public build and tests do not require the path once decoupled or removed.
- **generic catalog (proposed):** public build consumes vehicle-independent definitions (`uds/obd_catalog.yaml`, `uds/iso14229.yaml`, `faults/catalog.yaml`, `vss/overlay.vspec`, `dbc/platform.dbc`, `limits/platform_limits.yaml`) instead of CL250-specific bindings.
- **synthetic example vehicle (proposed):** public build and CI consume a non-proprietary synthetic vehicle pack (e.g., an example 1-cylinder motorcycle with fictitious constants and standard-only OBD DIDs) generated through the same public `tools/codegen` pipeline, while real CL250 packs live in a private repo (D-135 item 3).

## 3. Proposed Split Architecture (Summary — Proposed Only)

To keep the public thesis platform buildable, testable, and reproducible while isolating sensitive content (D-135 item 3):

1. **Public `vehicle-defs` (proposed):** retains `dbc/platform.dbc`, `vss/overlay.vspec`, `uds/{dids,iso14229,obd_catalog}.yaml`, `ble/ble_schema.json`, `privacy/position_rule.yaml`, `limits/platform_limits.yaml`, `faults/{catalog.yaml,alert_rules.yaml,i18n/*}`, `vectors/`, `safety/`, `requirements/`, `tools/codegen/`, and generic docs — plus a **synthetic example vehicle pack** (e.g., `vehicles/example_moto/`) so public `make check`, `make gen`, `make drift`, `make misra`, and every consumer's public CI stay 100% green without private credentials.
2. **Private vehicle-pack repository (proposed, e.g. `vehicle-pack-cl250`):** holds `dbc/cl250.dbc`, `uds/vehicle_cl250.yaml`, `vehicle/cl250_constants.yaml`, `vehicle/cl250_faults.yaml`, `derived/cl250_derived.yaml`, `docs/legacy-telemetry-notes.md`, `docs/ideas/cl250-technical-baseline.md`, `vehicle-ml`'s `configs/physics_cl250.toml`, and (when ready) CL250-specific trained models/adapters. Consumes public `vehicle-defs` `tools/codegen` via a lightweight CI job to stay well under the GitHub Free **2,000 Actions minutes/month** budget.
3. **Private legacy archive (proposed):** change visibility of archived `HondaCl250_Telemetry` from public to private (zero CI minutes needed since it is archived).
4. **Consumer build integration (proposed):** firmware (`rt-core`, `connectivity-node`), host services (`vehicle-server`, `vehicle-ml`, `vehicle-linux-node`), and UI (`vehicle-mobile`, `vehicle-analyzer`) default to the public synthetic example vehicle pack in public CI and accept a local/private vehicle-pack override path (e.g., via CMake variable, env var, or Vite alias) for real CL250 builds.

## 4. Open Questions for the User

No decision is made in this document. Before any file is moved or any repository setting is changed, the user needs to decide:

1. **Private repository topology:** Should all private vehicle packs, ML configs/weights, and future commercial modules live in one private repository (e.g., `vehicle-private` or `vehicle-packs`), or one private repository per vehicle/product (`vehicle-pack-cl250`, `vehicle-models-private`, etc.)?
2. **History rewriting vs. forward-only split:** Since CL250 files (`uds/vehicle_cl250.yaml`, `cl250_constants.yaml`, `HondaCl250_Telemetry`, and consumer submodule commits) have already been public, do you want a **forward-only removal** (new commits removing them from public `main`, accepting that git history and existing clones retain past commits) or an explicit **git history rewrite** (force-pushing rewritten history across `vehicle-defs` and/or consumers, which invalidates existing tags and submodule SHAs)?
3. **`HondaCl250_Telemetry` visibility:** Should the archived `HondaCl250_Telemetry` repository be switched to private now, or left public for thesis reference?
4. **Timing relative to hardware bring-up (Phase 0 / T6 / T13 / T16):** Should the split happen before the STM32 boards arrive (while `rt-core` and `connectivity-node` are still being prepared for first power-on), or after the first real CL250 capture (T16) so that newly discovered passive frames (`dbc/cl250.dbc`, Q-001) go directly into the private repo without ever landing in public git history?
5. **Android package ID and BLE branding:** Should `vehicle-mobile` (`com.honda.telemetry.cl250`, `"Honda-CL250"` scan prefix) and `vehicle-connectivity-node` (`"Honda-CL250-Telemetry"`, `"Honda-CL250-AP"`) be renamed to a brand-neutral default in the public repos, with CL250 branding injected only from a private build flavor/config?
6. **CL250 thesis documentation:** Which docs belong in the public thesis (`docs/hardware-integration.md`, `docs/img/hardware/06-cl250-placement.svg`, `docs/vehicle-work-plan.md`, `docs/ideas/cl250-technical-baseline.md`) vs. private (`docs/legacy-telemetry-notes.md`, `docs/archive/tr/*`)?
7. **Private CI budget & branch protection on GitHub Free:** Because private repos on the Free plan share 2,000 Actions minutes/month and have no repository rulesets, is a minimal private CI (codegen check + drift check only, running heavy MISRA/MSan/full-suite checks only on public repos) acceptable, or is a paid plan / self-hosted runner planned later?
